# WebMCP Challenge 企画・評価基準

最終確認日: 2026-08-27（JST）

この文書は、OpenAI WebMCP Challenge向けの企画判断、実装方針、提出要件をリポジトリ内で共有するための作業用まとめである。規約と日程について矛盾がある場合は、必ず [Devpost Official Rules](https://webmcp.devpost.com/rules) と主催者の最新告知を優先する。

## 1. Challengeの概要

WebMCPは、Webページが現在のページ上で利用できる操作を、AIエージェント向けの名前付き・型付きツールとして公開するための実験的なオープン標準である。

通常のブラウザ操作では、エージェントはスクリーンショットやDOMを解釈してクリック・入力位置を推測する。WebMCPでは、サイト側が次のような構造化された操作口を定義する。

```js
document.modelContext.registerTool({
  name: "example_tool",
  description: "このツールが何をするか",
  inputSchema: {
    type: "object",
    properties: {
      value: { type: "string" },
    },
    required: ["value"],
  },
  execute: async ({ value }) => {
    // 人間向けUIと共有するクライアントロジックを呼び出す
  },
});
```

Challengeの中心テーマは、単に「AIが操作できるWebサイト」を作ることではない。人間とエージェントが同じWebアプリ、同じ表示状態、同じ作業対象を共有することで、そのアプリが明確に良くなる体験を作ることである。

## 2. WebMCPを使う意味

### 通常のMCPとの違い

通常のMCPは、サーバー、ローカル環境、外部サービスなどのAPIやデータをエージェントに公開する用途に向いている。ブラウザでページを開いていなくても成立する処理は、通常のMCPやバックエンドAPIで十分な場合が多い。

WebMCPは、現在開いているページの次のような状態と結びつく。

- 未保存の編集内容
- 現在の選択範囲、フィルター、表示期間、ズーム位置
- ドラッグ中または仮配置中の要素
- 人間が反映、破棄した項目
- ページ内だけに読み込まれたローカルデータ
- エージェントが追加し、人間がこれから確認する変更

### Computer Useとの違い

Computer Useは、既存サイトを人間と同様にスクリーンショット、クリック、キーボード入力で操作する。サイト側の改修が不要である一方、UI変更や位置推定の影響を受けやすい。

WebMCPはサイト側が `name`、`description`、`inputSchema`、`execute` を定義する。エージェントは「Submitボタンを探してクリックする」のではなく、たとえば `submitForm({ ... })` のような正式な操作を呼び出す。

### 使い分け

| 手段 | 主な対象 | 適した状況 |
| --- | --- | --- |
| 通常のMCP / API | バックエンドや外部サービス | ページを閉じても同じ価値を提供できる処理 |
| Computer Use | 既存の人間向けGUI | サイトを変更せず、視覚的に操作する必要がある処理 |
| WebMCP | 現在のライブページ | 人間とエージェントがページ状態を共有して共同編集する処理 |

WebMCPは通常のMCPやComputer Useの置き換えではなく、現在のWeb UIを共同作業面として残すための選択肢である。

## 3. 公式の審査方法

### Stage One: pass / fail

最初に、次の最低条件を満たしているかが判定される。

- Challengeの「人間とエージェントがWeb上で協力する」というテーマに合っている
- WebMCPを実際に利用している
- アイデアと実装に最低限の実現可能性がある

ここを通らない場合、詳細な採点には進まない。

### Stage Two: 4項目を同じ比重で評価

| 公式評価項目 | 評価される内容 | このプロジェクトで示すべきこと |
| --- | --- | --- |
| WebMCP Leverage | WebMCPをどれだけ深く、巧みに利用しているか。非自明で実動する実装か | 現在のページ状態を読むだけでなく、複数の型付きツールでUIを安全に更新し、人間の操作を次の呼び出しへ反映する |
| Execution | 技術デモではなく、完全で一貫したプロダクト体験か | 初見でも目的が分かり、手動操作、エージェント操作、レビュー、最終結果まで破綻なく動く |
| Potential Impact | 実在する対象者の具体的な問題を解決するか | 誰が、いつ、何に困っていて、導入すると何が短縮・改善されるかをデモで証明する |
| Creativity & Ambition | コンセプトが新しく、既存例と異なるか | 既存の旅行、買い物、文書編集などの焼き直しではなく、WebMCPだから成立する共同作業を見せる |

4項目は同じ比重である。同点の場合は、上から順に比較されるため、最初の `WebMCP Leverage` が最重要のタイブレーカーになる。

## 4. このプロジェクト独自の企画判定基準

新しい案は、次の7条件をすべて説明できることを原則とする。

1. AIがいなくても、人間がそのWebアプリを使う理由がある
2. 人間が画面を直接操作することに意味がある
3. エージェントの変更が同じ画面へ現れ、人間が直接修正できる
4. エージェントが、人間による直前の修正・選択・破棄を次の処理に利用する
5. 一回の指示で完了せず、人間とエージェントの往復が価値になる
6. 通常のMCPやバックグラウンドAIでは、ページ状態の同期に追加実装が必要になる
7. Computer Useのクリック操作より、名前付き・型付きWebMCPツールの方が明確に安全・高速・確実になる

### 強い共同作業ループ

```text
人間がUIを直接操作する
  ↓
ページ内の未確定状態が変わる
  ↓
エージェントがWebMCPツールで現在状態を取得・更新する
  ↓
変更セットが同じUIにレビュー可能な状態で現れる
  ↓
人間が反映、破棄、修正する
  ↓
エージェントがその判断を使って次の処理を行う
```

### 不採用にすべき兆候

- ページを閉じても同じ価値を提供できる
- アプリの主目的がAIへの指示入力になっている
- エージェントの処理結果がチャットに返るだけで、ページへ反映されない
- 人間は最初に指示するか、最後に反映するだけである
- AIを外すとアプリ単体では用途がない
- WebMCPツールが、既存ボタンを一度押すだけの薄いラッパーになっている
- 通常のMCPやバックエンドAPIで同じ体験を簡単に実現できる

## 5. 採用するプロダクト

企画選定の結果、**Screen Blueprint Studio**を作成する。

再利用可能なUIコンポーネントをCMSのように組み合わせてワイヤーフレームを構築し、同じ構造化モデルから画面項目、状態、イベント、API、権限、テスト観点を管理・生成するWebアプリである。

自由描画型のワイヤーフレームツールではない。ワイヤーフレームは独立した画像ではなく、画面仕様モデルの視覚表現とする。人間とエージェントは同じキャンバス、選択中の要素、未保存ドラフト、変更セットを共有し、変更、修正、反映、破棄を交互に行う。

この案を採用する主な理由:

- AIなしでも人間が画面を構築し、仕様を確認・編集できる
- WFと仕様書を別々に更新することによる乖離を減らせる
- 現在の選択、未保存仕様、active change setなど、WebMCPと結びつくページ固有状態がある
- 人間の視覚判断とエージェントの網羅性・一括更新を明確に分担できる
- 仕様漏れ、状態、API、権限、テストまで扱うため、汎用AIワイヤーフレームとの差別化ができる

詳細なプロダクト方針、MVP、WebMCPツール候補、デモシナリオ、次の設計事項は [PRODUCT_DIRECTION.md](./PRODUCT_DIRECTION.md) を参照する。

## 6. これまでに見送った方向

| 案 | 見送った理由 |
| --- | --- |
| Consent Studio | アプリ単体の用途が弱く、責務の多くがエージェント、ブラウザ、フォームライブラリ側にある |
| Journey Studio | WebMCP開発・評価支援ツールとしては成立するが、人間とエージェントが実用アプリを共同利用するChallengeの中心テーマから離れる |
| RescueGrid | 想定需要と利用者像を具体的に証明しにくい |
| ShowFlow | 音声で作業を依頼してバックグラウンド実行するだけでも成立し、ライブページを共同操作する必然性が弱い |
| MapForge | WebMCPとの相性はよいが、作成者自身が課題・価値・完成像を評価しづらく、デモの説得力が下がる |
| Incident Canvas | 単なるログ要約やバックグラウンド分析へ寄りやすく、可視化の実装負荷も大きい |
| Reconcile Desk | 実務需要はあるが業務知識が必要で、Creativity & Ambitionの差別化が難しい |
| Constraint Scheduler | 最適化処理自体はバックエンドで成立し、ライブページ共有の必然性を示しにくい |

## 7. 実装時の品質基準

### 人間向けアプリ

- AIが接続されていなくても主要機能を手動で操作できる
- 初見で対象ユーザー、入力、操作、成果物が分かる
- エージェントが行った変更と人間が行った変更を視覚的に区別できる
- エージェントの変更セットを反映、破棄、修正、Undoできる
- ローディング、空状態、エラー、WebMCP非対応ブラウザを扱う

### WebMCPツール

- 読み取りツールと更新ツールを目的別に分ける
- ツール名とdescriptionだけで、いつ使うべきか判断できる
- inputSchemaに必須項目、enum、範囲、説明を設定する
- 人間向けUIと同じ状態管理・検証ロジックを再利用する
- ツール実行後、UIが即座に更新される
- 大きな一括更新を、レビュー前の未確定状態として扱える
- 反映前の変更セットと確定状態を分離する
- DevToolsでツール一覧、Schema、実行履歴、結果を確認できる

### 通常MCP / Computer Useとの差を示す

デモと提出説明には、最低でも次の一文を具体化して含める。

> このアプリでは、現在のページ内にある「○○」を人間とエージェントが共有するため、バックエンドMCPだけでは「△△」の同期が必要になる。Computer Useでは「□□」を画面から推測する必要があるが、WebMCPでは型付きの「××」ツールとして安全に実行できる。

## 10. 企画採点テンプレート

候補案を決定するときは、感覚だけで順位を付けず、次を各5点で採点する。

| 項目 | 0点 | 5点 |
| --- | --- | --- |
| WebMCP Leverage | 既存ボタンの薄いラッパー | ページ固有の未確定状態を複数ツールで読み書きし、人間との往復に使う |
| Execution | 技術デモだけ | AIなしでも使える一貫したプロダクト |
| Potential Impact | 対象者と問題が曖昧 | 実在する対象者、頻度、損失、改善が具体的 |
| Creativity & Ambition | 公式例の焼き直し | WebMCPだから成立する新しい共同作業 |
| 背景AIへの耐性 | ページを閉じても成立 | ライブページと人間の直接操作が不可欠 |
| デモ明瞭性 | 説明しないと価値が分からない | 3分以内に問題、往復、成果が視覚的に伝わる |

公式4項目の合計を優先し、そのうえで「背景AIへの耐性」と「デモ明瞭性」を企画上の品質ゲートとして使う。

## 11. 現在のリポジトリ状態

Screen Blueprint StudioのReact MVPを実装済みで、現在は提出品質を整えるフェーズにある。

- React、TypeScript、Vite、Zustandによる3ペインの画面仕様エディタ
- 複数screen、semantic component tree、state、event、API operationの構造化モデル
- 確定documentとpreview用effective documentを分離したreviewable change set
- 人間だけが行う反映・破棄、確定transactionのUndo
- read 4件、write 6件の計10 WebMCP tools
- `localStorage`永続化、破損データrecovery、保存不能時のJSON退避
- exact runtime validation、参照整合性、prototype-chain ID対策
- buildと21グループの回帰テストを通過

残作業は公開リポジトリとlive URLの準備、Chrome WebMCP testing環境での最終デモ確認、提出文と動画の作成である。
